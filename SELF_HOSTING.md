# Self-Hosting API Specification

The Make This Better Widget SDK can work with any backend that implements the
Submission Session API below. A Session temporarily holds the reporter's
context and optional clarification. Only finalization creates formal Feedback.

This document describes the HTTP contract used by Widget SDK 1.x. The full
Submission Session flow has five HTTP operations across four stages: create,
clarify (`POST` and `GET`), finalize, and abandon. A backend without AI can use
the three-operation profile described below.

| Profile | Required operations |
|---------|---------------------|
| No AI | Create, finalize, and abandon; return `ai_clarify_available: false` |
| AI clarification | All five Session operations |
| Reporter handoff | Either profile plus the two optional handoff operations |

## Quick Start

1. Implement the Session operations for your profile above.
2. Point the Widget at your API version root. Do not include `/widget` in
   `apiUrl`; the SDK appends the resource paths itself.

```html
<script src="https://unpkg.com/makethisbetter@1"></script>
<script>
  MakeThisBetter.init({
    projectKey: 'your-project-key',
    apiUrl: 'https://your-server.com/api/v1'
  })
</script>
```

If you serve the SDK from your own server as a single ESM file (an importmap
vendor copy, an asset-pipeline download), use the standalone build —
`https://unpkg.com/makethisbetter@1/dist/makethisbetter.standalone.js` — not
`makethisbetter.esm.js`. The split ESM file imports its screenshot renderer
from a sibling `./html-to-image.js` chunk, which a relocated or digested
filename cannot resolve; the standalone build inlines it.

If the host page enforces a Content Security Policy, its `connect-src` must
allow your API origin (`https://your-server.com` in the example above).
Interaction Replay's on-demand recorder script has its own `script-src`
requirements — see [Content Security Policy in the Widget
README](README.md#content-security-policy), including how to serve the rrweb
UMD file from your own origin instead of jsDelivr.

## Authentication and CORS

Every request includes the public Project Key:

```http
X-Project-Key: <projectKey>
```

Session requests also include a high-entropy token generated by the active
Widget instance:

```http
X-Submission-Token: <submissionToken>
```

Store only a cryptographic digest of the Submission Token. Scope every Session
lookup to the Project Key before authenticating the token. Treat the Project
Key and all identity fields in the request body as public, client-controlled
input; they are not proof of a reporter's identity.

If the host configures `userToken` or `userTokenFn`, the Widget also sends
`X-User-Token`. A self-hosted backend may define and verify its own token format.
Use verified token claims instead of `feedback[user_*]` values whenever the
token is valid. A backend that requires verified identity may return `403
Forbidden` when this header is missing or invalid.

For the minimum Session flow, CORS must allow:

- Headers: `X-Project-Key`, `X-Submission-Token`, `X-Idempotency-Key`,
  `X-User-Token`, `X-MTB-Capture-Policy`, `Content-Type`, and `Accept`.
- Methods: `GET`, `POST`, `PUT`, `DELETE`, and `OPTIONS`.

The optional reporter handoff endpoints require `X-Identity-Token` and `PATCH`
as described below.

### Optional Self-Hosted Image Proxy

The SDK first reads every screenshot resource from its original URL. Directly
readable images need no proxy. After an active Session exists, a failed
cross-origin raster image causes this optional request:

```http
POST /api/v1/widget/feedback_submission_sessions/:id/image_proxy_url
X-Project-Key: <projectKey>
X-Submission-Token: <submissionToken>
Content-Type: application/json

{"image_proxy_url":{"source":"https://cdn.example.com/photo.png"}}
```

Authenticate the active Session, validate the complete source URL, and return a
short-lived URL for your own image proxy:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"url":"https://your-image-proxy.example/signed?..."}
```

The returned URL must authorize one exact source without browser credentials.
Return the image bytes with their verified raster `image/*` content type and
CORS access for the host page. Treat the byte-serving endpoint as
SSRF-sensitive: allow only public HTTPS destinations on port 443; reject URL
credentials and IP literals; validate every redirect hop; cap redirects,
timeouts, and streamed response size; verify that the image signature matches
the declared MIME type; and never forward cookies, authorization headers, or
other browser request headers. Rate limit URL issuance by Project and source
IP, use short expirations, rotate signing keys, and filter source URLs and
signatures from logs.

If this endpoint is absent or rejects a resource, the SDK uses a transparent
placeholder for that image and preserves the rest of the screenshot. Images
that were directly readable never use the proxy.

`image-proxy.makethisbetter.dev` is private infrastructure for the hosted
MakeThisBetter service. Self-hosted installations must operate their own proxy
or omit this optional endpoint; the open-source Widget handles both cases.

## 1. Create a Session

### `POST /api/v1/widget/feedback_submission_sessions`

This endpoint captures context but must not create Feedback, notify the team,
publish to a board, or start triage.

```http
X-Idempotency-Key: <one key per reporter submission>
X-Submission-Token: <same token on every retry>
X-MTB-Capture-Policy: sensitive-data-v1
Content-Type: multipart/form-data; boundary=...
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `feedback[description]` | string | yes | Reporter's original text |
| `feedback[page_url]` | string | no | Page URL where feedback was captured |
| `feedback[user_agent]` | string | no | Full user agent string |
| `feedback[browser]` | string | no | Browser name and version |
| `feedback[os]` | string | no | OS name and version |
| `feedback[screen_width]` | integer | no | Screen width in pixels |
| `feedback[screen_height]` | integer | no | Screen height in pixels |
| `feedback[screenshot]` | file | no | PNG or JPEG screenshot |
| `feedback[recording]` | file | no | rrweb Interaction Replay JSON |
| `feedback[recording_duration]` | integer | no | Interaction Replay duration in seconds |
| `feedback[annotations]` | JSON string | no | Array of annotation objects |
| `feedback[console_errors]` | JSON string | no | Array of console error strings |
| `feedback[target_element]` | JSON string | no | Selected element object |
| `feedback[breadcrumbs]` | JSON string | no | Array of sanitized breadcrumb objects |
| `feedback[reporter_email]` | string | no | Reporter email |
| `feedback[reporter_name]` | string | no | Reporter name |
| `feedback[reporter_external_id]` | string | no | Reporter ID |
| `feedback[user_email]` | string | no | Host identity alias for `reporter_email` |
| `feedback[user_name]` | string | no | Host identity alias for `reporter_name` |
| `feedback[user_id]` | string | no | Host identity alias for `reporter_external_id` |

The capture-policy header is set by the SDK and is not a public configuration
option. It is a compatibility version signal, not an authentication credential
or proof that a binary attachment was filtered. Accept screenshot and Replay
attachments only when its value is exactly `sensitive-data-v1`. A request
without the current value is an older client: continue accepting and filtering
its text and structured context, but discard `screenshot`, `recording`, and
`recording_duration`.

Before storage, recursively replace high-confidence secrets in text and
structured fields with `[Filtered]`. Parse Replay JSON, apply the same filter,
and store only the re-serialized result. If Replay parsing or filtering fails,
discard the Replay and its duration without failing the Session. Reporter name,
email, and external ID are identity fields and remain unchanged.

The SDK's fixed browser policy preserves ordinary form values while filtering
passwords, payment-card data, CVV and expiry fields, OTPs, access tokens,
secrets, API keys, hidden/file values, Luhn-valid card numbers, JWTs, PEM
private keys, and common API-key formats. `rr-block` hides an entire marked
region; `rr-mask` hides its text and form-control content. Both markers apply to
screenshots, Interaction Replay, breadcrumbs, and annotation metadata. If
screenshot filtering fails, the SDK omits the screenshot and submits the text
Feedback.

Return `201 Created` for a new Session and `200 OK` when replaying the same
Idempotency Key with the same Submission Token. Reusing the key with a different
Submission Token should return `409 Conflict`.

```json
{
  "submission_session": {
    "id": "submission_abc123",
    "ai_clarify_available": true
  }
}
```

`ai_clarify_available` is required. Return `false` when the backend cannot ask
an AI clarification question; the Widget will skip clarification and let the
reporter finalize immediately. The server may echo the Widget-supplied `token`,
but the SDK ignores that field and continues using its locally generated token.

## 2. Clarify the Session

Do not expect clarification requests when Session creation returned
`ai_clarify_available: false`.

### State model

Every JSON clarification response uses this wrapper:

```json
{
  "clarification": {
    "status": "awaiting_response",
    "messages": [
      {"role": "assistant", "content": "What were you trying to export?"}
    ],
    "done": false
  }
}
```

| Status | Meaning | `done` |
|--------|---------|--------|
| `idle` | No clarification attempt has started | `false` |
| `processing` | A question is being generated; the Widget should poll | `false` |
| `awaiting_response` | The assistant has asked its one question | `false` |
| `completed` | The reporter answered or no further turn is needed | `true` |
| `failed` | An available clarification attempt failed and may be retried | `true` |

`messages` is always an array of `{ "role": "assistant" | "user", "content":
"..." }` objects. The Widget uses `done` to decide whether it can finalize and
uses `status` to decide whether to poll, enable input, or offer a retry.

### Start, answer, and retry

`POST /api/v1/widget/feedback_submission_sessions/:id/clarification` accepts
one of these JSON bodies:

```json
{}
```

Starts the initial turn. Return `200 OK` if the result is ready, or `202
Accepted` with `status: "processing"` when work continues asynchronously.

```json
{"message": "A PDF report"}
```

Records the reporter's one answer. Return a `completed` snapshot. Answering
never finalizes Feedback.

```json
{"retry": true}
```

Restarts a failed clarification attempt. Only `failed` Sessions should accept
this transition. Return `202 Accepted` with `status: "processing"` for queued
work, or a completed snapshot when handled synchronously.

Starting an already `processing` Session must not enqueue duplicate work. The
Widget first attempts SSE; if streaming is unavailable, it sends the start POST
again and falls back to polling.

### Poll

`GET /api/v1/widget/feedback_submission_sessions/:id/clarification` returns the
current wrapped clarification snapshot. The Widget polls while the status is
`processing`.

### Optional SSE response

For the initial `POST`, the Widget sends `Accept: text/event-stream`. A backend
may ignore that preference and return the JSON response above. The Widget does
not consume that first JSON body: it sends the idempotent start request again,
then uses the JSON and polling flow. Starting an already `processing` Session
must therefore return its current snapshot without starting duplicate work.

To stream, return `Content-Type: text/event-stream`. Emit zero or more `delta`
events followed by exactly one `done` event. Each event uses one JSON `data`
line:

```text
event: delta
data: {"text":"What were "}

event: delta
data: {"text":"you trying to export?"}

event: done
data: {"done":false,"messages":[{"role":"assistant","content":"What were you trying to export?"}]}

```

On failure, terminate the stream with:

```text
event: done
data: {"error":true,"done":true,"messages":[]}

```

Do not use `failed` to advertise a backend with no AI capability. Return
`ai_clarify_available: false` when creating the Session instead.

## 3. Finalize Feedback

### `POST /api/v1/widget/feedback_submission_sessions/:id/feedback`

This is the only operation that creates formal Feedback. It must be atomic and
idempotent: transfer the Session's description, context, clarification
transcript, screenshot, annotations, and Interaction Replay once, then clear
sensitive Session fields.

Return `201 Created` when Feedback is created and `200 OK` with the same Feedback
for a retry:

```json
{
  "feedback": {
    "id": "FB-1",
    "status": "received",
    "project_id": "acme"
  }
}
```

`id`, `status`, and `project_id` are required. `board_url` and `identity_token`
are optional hosted-board handoff fields. If they are omitted, the Feedback is
still submitted successfully and the Widget does not show a board link or email
capture. If `identity_token` is returned for an anonymous reporter, implement
the optional reporter update endpoint below.

The SDK automatically retries a network error or `5xx` once, so keep finalized
Sessions available long enough to return the same Feedback for an immediate
retry. The Make This Better hosted backend keeps this retry record for 15
minutes.

## 4. Abandon a Session

### `DELETE /api/v1/widget/feedback_submission_sessions/:id`

Return `204 No Content`. Clear sensitive fields and purge unattached blobs
without creating Feedback. Repeating an abandon may also return `204`; trying
to abandon a finalized Session should return `409 Conflict`.

Expire active Sessions 24 hours after creation. Do not describe this as an idle
timeout unless activity actually extends the expiration timestamp.

## Optional Reporter Handoff

These operations are not required for feedback submission. They support the
hosted-style anonymous "My feedback" link and post-submit email capture.

### Create an identity token

`POST /api/v1/widget/identity_tokens`

```json
{"reporter_external_id":"anon_abc123"}
```

Return `201 Created`:

```json
{
  "identity_token": "short-lived-token",
  "board_url": "https://feedback.example.com"
}
```

The Widget may call this on a later visit after it has cached a `board_url`.
Failures are ignored and hide the link.

### Update an anonymous reporter

`PATCH /api/v1/widget/feedbacks/:feedback_id/reporter`

```http
X-Identity-Token: <identityToken returned during finalization>
Content-Type: application/json
```

```json
{"reporter":{"email":"reporter@example.com"}}
```

Return `204 No Content`. Verify that the identity token belongs to the same
Project and reporter as the Feedback before updating anything. The Widget calls
this only when finalization returned an `identity_token` for an anonymous
reporter who has not already supplied an email.

## Error Responses

The Widget relies on HTTP status codes and does not currently display an error
response body. Use these statuses for compatibility:

| Status | When |
|--------|------|
| `401 Unauthorized` | Invalid or missing Project Key |
| `403 Forbidden` | Required host identity is missing or invalid |
| `404 Not Found` | Wrong Project, invalid Submission Token, or expired token |
| `409 Conflict` | Session is in an incompatible terminal state |
| `422 Unprocessable Content` | Missing or invalid input |
| `429 Too Many Requests` | Rate limit exceeded |

An error response may have an empty body. JSON errors are recommended for other
clients and operational debugging:

```json
{
  "error": "Description can't be blank. Fix the listed fields and retry.",
  "errors": {"description": ["can't be blank"]}
}
```

Never expose exception messages, class names, backtraces, credentials, or other
internal details in an error response.

## Versioning and Compatibility

`apiUrl` includes the major API version root. Widget SDK 1.x uses this `/api/v1`
contract. Backends should ignore unknown response fields so backward-compatible
fields can be added within v1. A breaking request, response, authentication, or
state-machine change requires a new API version and an explicit Widget SDK
opt-in; existing v1 behavior will be deprecated in SDK release notes before it
is removed.

## Hosted Platform Features

The Widget SDK and this HTTP contract are open source. The hosted platform adds
managed AI triage, Dashboard, Feedback Board, MCP/CLI/Skills, GitHub/Linear sync,
and reporter notifications. A self-hosted backend may implement its own versions
of those capabilities.
